# Lattice — Project Review Summary

**Prepared for:** External review via Claude.ai  
**Date:** 2026-05-15  
**Purpose:** Provide an honest, comprehensive account of a software project built collaboratively between a non-engineer product owner and Claude Code (Anthropic's AI coding assistant), for review and feedback on approach, productivity, and improvement opportunities.

---

## 1. Who is building this and how

**The builder:** A non-engineer product owner with strong product instincts and design sensibility. Not a developer — cannot write production code independently, but can read it, critique it, reason about architecture, and make informed decisions.

**The collaborator:** Claude Code, used as the primary development partner across all sessions. All code is generated by Claude Code with the user directing product decisions, reviewing output, and making strategic calls.

**Session structure:** Work happens in discrete sessions (typically 1–4 hours). Each session begins by reading `CLAUDE.md` (operating constitution), `PLAN.md` (living roadmap), and the latest session note. Sessions end with notes written, plan updated, and a clean commit pushed.

**No external engineering team.** This is a solo product owner working exclusively with AI tooling to build a production-deployed web application.

---

## 2. What we're building

**Lattice** is a personal Life OS — a multi-domain system for one person to manage their life across property, finances, career, health, and other domains with shared context and a trusted AI assistant at the center.

It started as **Parcel**, a property management application. As it matured, the vision expanded to a broader system. Parcel became the first domain within a new top-level product called Lattice.

**Current live domains:**
- **Parcel** — property and household operations (fully functional, in production)
- **Sow** — kitchen garden management (migrated from a standalone app, completed this week)
- **Arc, Bloom, Form, Tend** — named and designed, not yet built
- **Control Panel** — admin module (owner-only, coming next)

**What makes this architecturally interesting:**
- Multi-tenant from day one (Supabase RLS, owner/member roles) despite being a personal tool
- Shared global context layer across domains (finances, time, goals) rather than disconnected apps
- JSONB data model for domain-specific state (flexible, avoids premature schema lock-in)
- Staged AI autonomy model — agents earn trust, never operate blindly
- Designed for one owner's real use, but structured to be marketable someday

## 3. Technical stack

- **Next.js 15** (App Router) — frontend and backend unified
- **Supabase** — Postgres + Auth + Row Level Security (free tier, ~30 migrations run)
- **TypeScript** throughout; build must stay clean at all times
- **Anthropic API** — Claude Sonnet 4.6 for complex reasoning, Claude Haiku 4.5 for narrow sub-tasks
- **Vercel** — hosting, auto-deploys on push to `main`
- **Tailwind / shadcn/ui** — Parcel uses these; Sow uses inline styles deliberately
- **No ORM** — direct Supabase queries throughout

## 4. Project arc — what was built and when

### Before sessions began
Parcel existed in some form — a property management app with projects, tasks, assets, budgets, timeline events, a property agent, and multi-user architecture.

### Phase A — Parcel Stabilization (April 2023)
The first sessions focused on hardening what existed before expanding.

**A1 — Defect resolution:** Six bugs from real user testing (the user's partner Erin and his father) were fixed: agent recommending past dates, a 3D visual hardcoded to one property, property dropdown not appearing for new users, floating chat and agent tab maintaining separate conversation histories, a drag-and-drop visual artifact, and agent responses being too verbose.

**A2 — Route hardening:** The ~1,200-line agent `route.ts` monolith was extracted into tool modules. Dynamic-ID routes reviewed for explicit property scoping.

**A3 — Technical guardrails:** Validation strengthened on critical routes, restricted-zone rules documented and followed.

**A4 — Baseline observability:** Logging and failure capture established for debugging.

*Key decision: stabilize the mature domain before expanding. This was the right call — the defect fixes were meaningful real-use improvements, not theoretical.*

### Phase B — QA Foundation
A QA backbone was built before introducing admin-agent-led evolution.

- **Fast review path:** Build, typecheck, lint, route verification, auth/permissions checks, scoping checks — all triggerable as a slash command (`/qa`)
- **Deep review path:** Simulated user flows, onboarding review, property workflows, agent quality checks
- QA report format defined and stored in-repo

*Key decision: QA before autonomy. Admin agents without a good observability base become narrators, not operators.*

### Phase C — Lattice/Workspace Core Architecture
This was the major structural expansion — from Parcel-as-product to Lattice-as-product.

**C1 — Workspace entity:** `lattices` table introduced (1:1 with user, strictly private). `lattice_id` FK added to `properties`. `member_role.viewer` renamed to `member_role.member`. `lib/get-lattice-id.ts` added. Auto-creation on first property creation. Migration 028.

*Key decision locked here: Lattice is 1:1 with a user — not a shared workspace. Each person has their own Lattice. Parcel members (collaborators) do not see the owner's Lattice and can have their own independently. This was a careful multi-user model decision.*

**C2 — Global Context foundation:** `global_context` table (JSONB fields: goals, planning_assumptions, risk_preferences, thresholds) and `global_commitments` table (structured rows for major financial commitments). Owner-only RLS. API routes: GET/PATCH global-context, GET/POST/PATCH/DELETE global-commitments. Migration 029.

**Parcel Z (interleaved):** Zones (replacing JSONB zones in site_config) and Spaces (replacing Rooms) as proper DB tables. FK linkage for projects, tasks, assets, ongoing tasks. `ongoing_task_instances` table for annual cycle tracking. Migration 030.

**C3 — Shared planning model:** `GET /api/global-context/summary` — derived planning layer with financial rollups, conflict detection, upcoming pressure points, and threshold violations. No new DB tables — computed from existing data.

**C4 — Lattice shell:** App shell and navigation restructured to reflect Lattice as the top-level product. `/lattice` home page built. Parcel becomes a domain within the nav, not the root.

*The initial C4 rollout was unsatisfactory — too close to a relabeled Parcel. A full redesign session followed: replaced with a proper hub page (seven module widgets, warm amber background, centered wordmark "Your personal operating system"). Login page rebranded to Lattice with a geometric lattice grid SVG. This revision was one of the better sessions — the user had a clear design direction and the execution was tight.*

**Domain naming (mid-C4 revision):** All seven hub domains named in a single focused session: Parcel, Arc, Bloom, Form, Tend, Sow, Control Panel — each with a color, icon, and framing philosophy. "Tend" for finances was a standout: finances as a garden you tend, not the focal point but kept healthy so it provides when needed.

### Sow domain migration (2026-05-15, just completed)
A standalone garden management app (plain HTML, Supabase, hardcoded API keys, PIN auth) was migrated into Lattice as a full module.

**Scope decision:** Full rewrite as a React component within Lattice, not an iframe or link-out. Lattice auth is the only gate — no separate login.

**Data migration outcome:** The old app had a bug — its Supabase `id=eq.singleton` filter failed silently (UUID type mismatch) and fell back to browser localStorage. The Supabase table was empty. Decision made to start fresh. All structural/agronomic data lives in TypeScript constants; only user state (status, tasks, logs, photos, overrides) is stored in the DB.

**Plot editability:** A key design insight — the user needed to be able to change what's planted in a plot (e.g., swap a pepper for a bean) without editing code. Solution: `plotLabels` and `plotThemes` overrides stored in the JSONB blob. An "Edit" tab in the plot side panel lets the user rename any plot and change its color theme. This satisfies both the immediate use case and next-season replanning.

**Mobile responsiveness:** The original implementation was desktop-only. Fixes: full-screen panel overlay on mobile (vs. 360px inline panel on desktop), compressed header, horizontal scroll for the Gantt timeline, abbreviated tab labels.

## 5. Governance and operating model

### CLAUDE.md — Operating Constitution
A detailed document committed to the repo that Claude Code reads at the start of every session. Covers:
- What the product is and its architectural principles
- Domain definitions and scope
- Agent model (user-facing vs. admin)
- Restricted zones (schema changes, auth, infra, external integrations — all require approval)
- Cost discipline (anything over $1 requires disclosure)
- Working style expectations (be direct, flag tradeoffs, prefer one slice at a time)
- Debugging expectations (structured, not looped guessing)

### PLAN.md — Living Roadmap
Tracks current state, what's complete, what's next, and a decisions log with rationale. Updated at the end of every meaningful session. The decisions log is particularly valuable — it records not just what was decided but why.

### SESSION_NOTES/
~20 session notes covering the full project arc. Each note records what was built, key decisions made, open questions, and the exact starting point for the next session. This continuity mechanism works well — a new session can orient quickly without re-reading all prior code.

### Commit discipline
Logical commit chunks (not one giant commit per session). Commits pushed at the end of each session; Vercel auto-deploys. TypeScript build must be clean before any commit.

## 6. Collaboration patterns — what works

**Clear product direction before build sessions.** The user consistently makes design decisions before implementation starts. Domain naming, architectural choices, and UX decisions are settled conversationally before code is written. This prevents wasted implementation work.

**Real user testing.** Phase A's defect list came from actual users (Erin and Dad) using the app in production. These were genuine friction points, not imagined bugs. Fixing them informed how the system should behave, not just what it should do.

**Staged commits.** Work is broken into logical chunks rather than one massive session-end commit. The decisions log in PLAN.md means rationale doesn't get lost.

**Willingness to redesign.** The C4 rollout was described as "not what was expected" and a full redesign session followed rather than trying to patch the original. The redesigned hub is substantially better.

**Strong product instincts on naming and framing.** The domain naming session produced seven names that each carry a philosophy, not just a label. "Tend" for finances is a good example — the framing shapes how the domain will be designed when it's built.

**Cost-consciousness.** Haiku vs. Sonnet routing is deliberate throughout. The CLAUDE.md cost discipline rule ($1 threshold for approval) is a real guardrail.

## 7. Collaboration patterns — what could be better

### The 10-hour no-code session
The single most significant productivity failure in the project: during the Sow migration, the user left Claude Code to work autonomously for ~3 hours. When they returned, Claude Code had spent the time reading files and planning rather than writing any code. No files had been created.

The root cause was insufficient direction-setting before stepping away. The task was scoped ("do the Sow migration") but without explicit instruction to start writing immediately and without permission to make reasonable decisions without approval. The result was a planning loop that never converted to execution.

**Lesson:** For autonomous long-running work, be explicit: "write all files now, make reasonable decisions, flag blockers as comments." Vague scope with no output format leads to analysis paralysis.

### Migration troubleshooting that required iteration
Several database migrations required multiple attempts due to pre-existing state (wrong schema, missing columns, UUID type mismatches). This is partly unavoidable in a live production system, but clearer pre-flight checks (querying existing table structure before writing migration SQL) would reduce retry loops.

### Trailing context accumulation
Long sessions with multiple tab changes and file reads accumulate context that can make Claude Code slower and less precise by the end. The project handles this reasonably well through session notes, but there's room to be more deliberate about starting fresh sessions when context is heavy.

### Data model assumptions
The Sow data migration revealed an assumption that had never been verified: the user believed garden data was in Supabase, but it was actually in browser localStorage due to a silent bug in the old app. A pre-migration verification step would have surfaced this faster.

## 8. Architecture decisions worth reviewing

**1. Inline styles for Sow instead of Tailwind**
Deliberate choice to avoid Tailwind config dependency in the new domain. Consistent with the original garden agent's approach. Tradeoff: more verbose JSX, no design system consistency with Parcel. Could become a maintenance problem if Sow grows significantly.

**2. JSONB blob model for domain state**
Sow stores all garden state in a single JSONB column per lattice. Fast to prototype, flexible, avoids premature schema. Tradeoff: no queryability, all or nothing on read/write, harder to do field-level RLS. The right call for now, but will need rethinking if Sow grows to multiple users or cross-domain references.

**3. Client component SPA for Sow**
`/sow` is a single `'use client'` component with all tabs and state. Simple to reason about, no server component complexity. Tradeoff: no SSR, slower initial paint, large bundle. Acceptable for a personal tool with infrequent cold starts.

**4. Lattice is 1:1 with a user**
This was the right simplification. The alternative (shared Lattice/workspace model) would have added significant complexity with no clear current benefit. The architecture keeps the door open for future shared access while not being forced to implement it now.

**5. Constants for agronomic data, DB for user state**
Sow's plot definitions (names, positions, timings) are TypeScript constants. User customizations (label overrides, theme overrides, status, logs) are in the DB. This is the right split — the constants change rarely and benefit from code review, while user state changes constantly and needs persistence.

## Summary for reviewer

This project represents a sustained, structured attempt to use AI coding assistance as a complete substitute for an engineering team. The governance model (CLAUDE.md, PLAN.md, session notes) is unusually disciplined for a solo/AI project. The product vision is coherent and the architecture is structurally sound.

The main failure modes observed are: (1) underspecified autonomous tasks leading to planning loops instead of execution, and (2) assumption-driven debugging (verifying the premise before starting the fix). Both are collaboration patterns that can be improved with deliberate practice.

The work done is real — a production-deployed application used by real people, with 30+ migrations, a functioning AI agent, multi-user auth, and a coherent multi-domain architecture. The pace from initial sessions to the current state represents roughly 3–4 weeks of part-time sessions.
